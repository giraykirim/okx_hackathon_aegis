# AEGIS pitch and hard jury Q&A

## Two-minute pitch

Trading agents can repeat an uncertain order, act on an old snapshot, confuse a model answer with permission, or leave an incident without an audit trail. AEGIS gives trading-agent developers a reusable operational checkpoint and a reference autonomous loop. It collects actual public market facts through official OKX Agent Trade Kit tools, records operational model availability, obtains a bounded EVREN proposal and applies a deterministic Python gate. It either sends nothing or, only with separately verified demo permissions, could enter the bounded demo path. Today's real demonstration sends nothing.

Show one Start: real ATK observation → LAN LAYA REVIEW/abstention → EVREN → policy → NO_TRADE → verification → audit. The event trail gives source timestamps, hashes, durations and correlation. Show the external API: a small request returns UNAVAILABLE because customer account facts are unknown; an excessive request returns BLOCK. Caller-supplied permission text cannot override either result.

Show Avalanche: actual ERC-8004 Agent #273 and a separately deployed contract anchoring one recorded HALT digest. Reasoning stays off-chain. The receipt verifies a recorded commitment, not prediction quality. We propose USD 0.01/check or USD 99/team/month, to test with consenting developer teams. No customers, revenue, permanent hosting or OKX listing are claimed. A temporary restricted HTTPS service has been tested. The concrete next gate is a protected HTTPS sandbox plus provider onboarding, not a promise of trading profits.

## Questions we should be able to answer directly

1. **How is this different from an exchange rejecting a bad order?** Exchange validation checks the request it receives. AEGIS adds pre-submission policy, cross-cycle deduplication/UNKNOWN blocking, explicit model/data availability and an attributable audit trail. This is demonstrated functionality, not proof of competitive uniqueness or avoided losses.
2. **Why pay for it instead of writing an if statement?** Teams may value integration consistency, durable retry handling and incident reconstruction. Willingness to pay is untested; the pilot measures integration time, repeated usage, reason usefulness and cost. A single simple check alone would not justify the proposed subscription.
3. **Are the proposed prices real revenue?** No. USD 0.01/evaluation and USD 99/team/month are hypotheses. Billing, subscriptions, signed customers and revenue are not implemented. Model analysis costs must be measured separately.
4. **Is this a buy/sell signal or delegated order authorization?** No. The public API's execution_authorized is always false. ALLOW_FOR_FURTHER_CHECKS, if ever supportable with independently bound account facts, would still not authorize an order. Current unknown accounts produce UNAVAILABLE/BLOCK.
5. **What happens if my request says my balance is huge and approval=true?** Requester context is untrusted and ignored. Private-balance/credential fields are rejected. The service fetches its own public ATK facts and never borrows the operator's account to approve a caller.
6. **Does the real notional API actually use the risk engine?** Yes. It calls the same Python policy.check used by the agent, strips accidental account fields and tests freshness, sizing, lot precision, instrument and quote integrity. Assessment-derived quantity is not an executable recommendation. MOCK is explicitly separate and deterministic.
7. **What does the agent do without per-step prompts?** One authenticated Start runs observe, classify, reason, risk, no-trade/action, verify and audit. We demonstrated a real MARKET_ONLY cycle and deterministic Stop. Tool execution is constrained to official allowlisted tools; the model cannot execute arbitrary commands.
8. **Why is LAYA abstaining if your model connection works?** The deployed LAN service accepts the envelope, but legacy Observation lacks trusted approval/journal/proposal context. REVIEW plus abstention is the correct supported fallback. The post-proposal context builder is inactive pending coordinated mapping; missing facts stay null.
9. **What does LAYA training or 236 offline tests prove?** Person 2 reported those engineering/dataset checks; they do not prove independent predictive success. The selected checkpoint remains base. A real synthetic full-context probe returned confidence 0.0035, while the backend needs at least 0.8 and other independent permissions. We claim transport/schema/version evidence, not a successful trained safety classifier.
10. **Were human labels changed to match your code?** No. Sixteen stale/future examples keep human REVIEW; four no-intent/unknown-permission examples keep CONTINUE for monitoring. The deployed ML policy still differs in those stale/future cases and needs a versioned revision. Python still vetoes stale/future execution; operational CONTINUE is never permission.
11. **What if EVREN is rate-limited, returns malformed JSON or follows malicious tool text?** Calls have deadlines/byte/request budgets; response proposals are schema validated and tool calls are rejected. 429, timeout or invalid output leads to deterministic no-trade/fallback. Arbitrary tool/news text cannot set trusted authorization or integrity flags. This is tested defense, not an unlimited adversarial robustness guarantee.
12. **What if the exchange times out after submission?** Journal the intent before submission, reconcile by the same client ID and do not place again. UNKNOWN blocks future orders across runs/restarts. A read timeout before any submission is NOT_SENT, a different state. Offline isolated tests cover the distinction; no real ambiguous order was deliberately created.
13. **Does accepted or partially filled mean success?** ACK/live and partial fill remain PENDING/unresolved. Filled, canceled and mmp_canceled can be VERIFIED terminal states after matching readback. VERIFIED does not mean filled; we preserve the venue state and never invent an order ID.
14. **Have you placed real-money or successful demo orders?** No live money is enabled. Actual official public reads and a separate read-only demo-account preflight are evidenced. Demo submission and reconciliation remain NOT_TESTED. Read-only disabled execution in System Status is an intentional boundary, not a green trading claim.
15. **Are you already listed or approved on OKX.AI?** No. Official ASP/A2MCP documentation supports a plausible standardized API route. Temporary HTTPS and official account login/ASP eligibility passed; durable hosting, registration/review and marketplace authentication compatibility remain missing. A free pilot could avoid x402, while paid settlement would require a separate integration. See the authoritative-source readiness matrix.
16. **Is your Fuji identity the same as OKX provider registration?** No. ERC-8004 Agent #273 is an on-chain identity on Fuji. It does not establish an OKX Agentic Wallet ASP account, listing, customer demand or model accuracy.
17. **What exactly runs on Avalanche?** Identity and a SHA-256 decision-receipt contract. ATK, EVREN, LAYA and Python policy run off-chain. The receipt lifecycle and actual fees are verified; submission-to-confirmation latency was not measured. No custom L1 or interchain messaging is claimed.
18. **Is the product publicly deployed?** The application currently runs locally, LAYA on a separate LAN machine, and contracts/metadata publicly. A restricted risk API has a temporary Cloudflare HTTPS hostname with real health/auth/private-route tests. The dashboard is local. Durable hosting, uptime and a second-device independent test remain NOT_TESTED. We do not present a Gist or contract deployment as a hosted FastAPI product.
19. **How do you prevent a public frontend from trading?** BFF controls require separate server and caller operator secrets. A public judge deployment leaves them absent. The restricted public backend forwards only health, descriptor and authenticated assessment; controls/private audit/tools return 404 even with an operator token. Secrets stay server-side, and demo configuration is rejected for that entrypoint.
20. **What do you store, and can you delete customer data?** Sanitized events, effective intent and cached responses persist locally in SQLite. Caller context/private provider bodies/hidden reasoning are not retained. Automatic expiry, tenant isolation and a deletion portal are not implemented; a dedicated consenting pilot needs an agreed manual retention procedure. Public chain commitments cannot be represented as erasable private records.
21. **What is the latency and production SLA?** One captured real cycle took 12.745448 seconds; its Python policy check measured about 0.300 ms. That is one sample, not p95 or an SLA. This prototype is a seconds-scale operational checkpoint, not HFT infrastructure.
22. **What must happen before launch?** Resolve LAYA policy/mapping, provision a real protected HTTPS host, test it externally, add tenant key lifecycle/retention operations, measure cost/latency and customer value, then submit actual OKX provider registration/review; wallet login and eligibility already passed. No security veto should be relaxed to make a status panel green.
